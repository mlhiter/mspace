# AGENTS.md

This project is the runnable local MVP workspace for mspace.

## Product Direction

mspace is an Inbox and Issue workspace for coding agents. It lets a team manage work as document-style issues, run development sessions through registered runtime workers, and deploy or validate those changes in a real namespace-scoped Kubernetes environment.

The product should stay narrow:

- interaction inspiration: Multica-style inbox, issue, and teammate workflow;
- technical inspiration: Optio-style Kubernetes runtime and git worktree isolation;
- core difference: document-first issue collaboration with attachable real test environments for coding agents.

## Current Implementation

- Desktop app: Electron, electron-vite, React 19, TanStack Router, React Query 5, Tailwind CSS 4, TypeScript.
- Public website: Vite, React 19, Tailwind CSS 4, and lucide-react in `apps/website`, deployed through Vercel with the root `vercel.json`. It has a homepage, a static `Changelog` navigation view backed by `apps/website/src/changelog.ts`, and a `Download` view that links to packaged desktop installers on GitHub Releases; the nav logo uses `apps/website/src/assets/mspace-mark-transparent.png` inside its own gray-white tile.
- UI system: shadcn/ui source components in `packages/ui/src/components/ui`, Radix UI primitives, lucide-react icons, Material Icon Theme file icons for file surfaces, shared exports through `@mspace/ui`, and shared desktop localization through `@mspace/i18n`.
- Workspace tooling: pnpm workspaces and Turbo.
- Server control plane: Go and chi. Team/shared server deployments use PostgreSQL through `pgx` with embedded migrations under `server/internal/control/migrations`; packaged personal desktop mode can run the same server contract on a server-owned SQLite snapshot store.
- Runtime worker: standalone Go daemon in `worker/` that registers with the server using an `msw_...` token, heartbeats, claims matching runtime tasks, completes protocol smoke/noop tasks, runs Codex-backed system Workflows such as `issue_type_triage`, and runs user `agent_session` tasks through fixed engine adapters for Codex, Claude Code, or Pi. Worker Core owns repo cache/workdir preparation, server-provided Skill materialization, artifact handling, source capture, cancellation, and result assembly; adapters own CLI launch/protocol/terminal evidence and opaque engine refs. For personal local projects, the worker resolves the git root for the repo cache, creates the session worktree from that root, then runs the selected engine from the configured project subdirectory. Docker-backed workers keep target project source under the worker root volume, such as `/var/lib/mspace-worker/repos` and `/var/lib/mspace-worker/workdirs`, instead of editing the host checkout directly.
- Runtime has two intended deployment forms behind the same control-plane protocol: a fixed Server Worker for personal or team environments, and a later Kubernetes Runtime Provider that creates isolated per-session Pod/Job workspaces. Do not fork the issue/session/log/evidence/PR model by backend; both forms should use `runtime_tasks`, runtime task events/logs, cancellation, and the same session/evidence handoff.
- The control plane owns users, local password credentials, workspaces, workspace membership, mspace auth sessions, GitHub identity, workspace GitHub App installation state, projects, project runbooks, project test cases, test case revisions, test case proposals, test plans, test runs, issues, child issue tasks, comments, reactions, labels, Inbox receipts, the fixed Agent catalog contract, built-in workflow skill catalog, workspace custom workflow skills, skill revisions, built-in skill settings, workspace settings, environments, clusters as Kubernetes environment compatibility records, issue test environments, issue handoffs, agent sessions, runtime registration tokens, runtime worker liveness/capability snapshots, runtime task logs/results, and the server-side runtime task queue. Agent definitions are code-owned and are not persisted per workspace.
- Storage stays server-owned. Team/customer/shared deployments use Postgres. The packaged personal desktop path may use `MSPACE_STORE=sqlite` and `MSPACE_SQLITE_PATH=<Electron userData>/mspace.db`; that is a local personal server store, not a renderer store, sidecar API, or team collaboration backend.
- Local username/password auth works in restricted or offline environments, while GitHub sign-in remains an optional external identity provider. Either route creates or returns an mspace user, signs an `msp_...` product session, returns an explicit auth `identity.provider`/`identity.login`, and gives the user a personal workspace by default. Open registration must not grant team workspace creation or shared server runner access.
- The desktop shows GitHub sign-in only for an explicitly configured team server, either from `MSPACE_SERVER_URL` or a saved Team server URL, when that server's `/health` response includes `capabilities.githubAuth: true`; that requires `MSPACE_GITHUB_CLIENT_ID`, `MSPACE_GITHUB_CLIENT_SECRET`, and `MSPACE_GITHUB_REDIRECT_URI` to all be configured. GitHub App automation is a separate capability: `/health` reports `capabilities.githubApp: true` only when `MSPACE_GITHUB_APP_ID`, `MSPACE_GITHUB_APP_CLIENT_ID`, and `MSPACE_GITHUB_APP_PRIVATE_KEY` are configured. Default packaged personal SQLite mode starts on local account creation and stays local-account-only, even if the default local dev server has OAuth variables. To debug GitHub OAuth against `127.0.0.1:8787`, launch with `MSPACE_SERVER_URL=http://127.0.0.1:8787 pnpm dev:desktop`.
- Server admin status is matched by configured auth login, not email. `MSPACE_SERVER_ADMIN_LOGINS` and `MSPACE_BOOTSTRAP_ADMIN_LOGIN` define who may create team workspaces; `MSPACE_BOOTSTRAP_ADMIN_LOGIN` plus `MSPACE_BOOTSTRAP_ADMIN_PASSWORD` can create the first local admin account on server startup. Customer Helm installs may also set `MSPACE_BOOTSTRAP_TEAM_WORKSPACE_NAME` plus `MSPACE_BOOTSTRAP_RUNTIME_TOKEN` so startup creates or finds one admin-owned team workspace and registers the fixed worker token for it. Ordinary users can only enter team workspaces through owner/admin invitations.
- Desktop GitHub sign-in starts at `GET /api/auth/github/start`, opens the returned GitHub URL in the browser, lets the server-side callback complete OAuth, then polls `GET /api/auth/github/result?state=...` for a single-use OAuth result containing the normal `msp_...` product session token. Desktop password auth posts to `/api/auth/password/register` and `/api/auth/password/login`. Do not move the GitHub client secret into Electron or workers.
- The renderer stores the mspace session token under `localStorage["mspace.authToken"]`, a lightweight display identity under `localStorage["mspace.authIdentity"]`, and the selected UI locale under `localStorage["mspace.locale"]`. Account-type UI should use the server auth identity provider; do not display GitHub as connected just because `user.email` is empty, since password accounts intentionally leave canonical email blank. Account profile editing lives on the Account Settings route, goes through server `PUT /api/auth/me`, and may update only display `user.name` and `user.avatarUrl`, never `identity.provider` or `identity.login`. When the stored personal workspace name is still the generated default `...'s workspace`, the left workspace menu may derive its display label from the current `user.name`; this is presentation-only and must not mutate the workspace record on profile save.
- The Electron main process chooses the server in this order: `MSPACE_SERVER_URL`, saved Team server URL from Electron user data, then the local bundled/dev server on `127.0.0.1:8787`. It starts the local server only for the default personal path and checks `/health` for protocol/capability compatibility before using a local or remote server. Personal desktop workspaces proactively ensure one generic host-local personal worker after auth and workspace selection without launching Chrome. Electron discovers installed `codex`, `claude`, and `pi` executables without running them and advertises only the matching `codex`, `claudeCode`, and `pi` capabilities; an explicit Codex action still requires a Codex auth file, while Claude Code and Pi authentication failures are reported by their adapters. Action-level preflight asks the server runtime availability API for the selected engine capability and asks Electron main to idempotently ensure only personal workers in personal mode. When `browser` or `chrome_cdp` is explicitly required, Electron keeps the generic worker running and starts a separate browser-capable companion worker against the same credential file, with its repo cache and workdirs isolated under `<Electron userData>/worker/browser-companion`. It never auto-starts a worker for team workspaces.
- Sidebar navigation currently exposes Inbox, Issues, Tests, Agents, Environments, and Projects, plus a workspace menu entry for Workspace Settings, a global search / Command+K palette for issues and projects, a quick link that opens issue creation from the left rail, and an Active work block for non-terminal issues plus plan-level summaries of actionable test-run activity. Active work should show user-recognizable objects: issue titles or test plan titles, with run/session details only as secondary context.
- Inbox is a review-only feed for per-user workspace issue events. The server control plane stores `issue_events`, `issue_event_receipts`, and `issue_watchers` for signed-in personal and team workspaces.
- Runtime registration credentials use the `msw_` prefix and are created from the server control plane for personal and team workspaces. Workspace Settings `Connect environment` creates a short-lived bootstrap credential, returns a one-time install command backed by `GET /install/worker`, and is the normal interactive team worker setup path; Helm-managed fixed workers can instead use `bootstrap.teamWorkspace.enabled=true` so the chart creates or reuses `MSPACE_RUNTIME_TOKEN`, the server registers it against the bootstrap team workspace, and the worker reads the same Secret key. Raw credential endpoints remain for Electron personal-worker lifecycle, API recovery, and debugging. Registered workers report name, mode, version, capabilities, labels, status, load, and heartbeat time through `runtime_workers`. The server runtime availability API is the product-facing preflight contract for `ready`, `stale_heartbeat`, `missing_capability`, `worker_draining`, `worker_offline`, `no_worker`, and `wrong_runtime_mode`; UI action readiness should use that contract rather than reimplementing heartbeat TTLs. Worker mode and task `runtimeMode` must match the workspace kind: personal workspaces use personal workers, and team workspaces use team workers. Server-side `runtime_tasks` can be queued through product flows or API/debug tooling, claimed by eligible online workers, cancelled by workspace users, advanced through claimed/running/final states by the claiming worker, and inspected through `runtime_task_events` plus worker-appended `runtime_task_logs`.
- Issue Detail exposes only `@codex`, `@claude`, and `@pi`. The renderer resolves project attachment, derives the exact engine capability, verifies a matching active worker, writes the human comment, then calls `POST /api/workspaces/{workspaceID}/issues/{issueID}/sessions` with `agentEngine`; the server repeats project, engine, runtime-mode, and worker checks. Issue comments may reference enabled server-managed workflow Skills with `/slug` or `#slug`; clients send only `skillSlugs`, and the server pins the bundles. When accepted, the server creates one provider-neutral `agent_session` runtime task, and the worker returns `agentEngine`, `engineSessionRef`, and `engineRunRef`; Codex also keeps historical thread/turn aliases. While a session is active, Issue Detail may show only the latest normalized `agent` message in one fixed-height activity row and must not promote command, reasoning, plan, file, tool, status, or diagnostic logs. Automatic issue analysis remains a distinct Codex-backed system Workflow using the server-owned `think` Skill, a read-only sandbox, and disabled source capture.
- The server control plane must stay Agent-runtime-free. It may queue `runtime_tasks` requiring `codex`, `claudeCode`, or `pi` and attach server-owned Skill bundles, but it must not install Agent CLIs, start Agent processes, execute Skills, or depend on Agent credentials. Authentication and configuration belong only to worker runtimes. The current Kubernetes fixed-worker image remains Codex-specific and mounts a Codex home Secret; multi-engine worker images are not implied by the generic protocol.
- Agent subprocesses must never inherit control-plane or Worker registration credentials. Helm Workers receive only their runtime token rather than the server Secret, and Worker launch code strips parent `MSPACE_*`, database, PostgreSQL, and GitHub token variables before appending the server-owned session environment. Public runtime-task debug APIs must not create raw `agent_session` tasks; those payloads are constructed only through the Issue Session and system Workflow paths.
- The left workspace menu is the primary place to switch workspaces, create a team workspace for server admins, open Account Settings, open Workspace Settings, and switch the desktop UI language between English and Simplified Chinese. Workspace Settings exposes current-workspace identity editing for team owners/admins, automation including opt-in automatic test-environment deploy after a source session captures a commit, team-only Team access for members/one-time `msi_...` invitations, `Connect environment` worker install commands, credential audit history, worker liveness/capabilities, issue-linked runtime tasks, task events, and worker logs. The normal UI should not expose a generic "queue runtime task" button; keep manual task creation to API/debug paths.
- The issue creation modal, Issue Detail reply composer, Project runbook editor, and Issue Detail runbook modal use `IssueDocumentEditor`, a TipTap-backed Markdown editor/viewer in `packages/views/src/issue-document-editor.tsx`, so document writing stays rich while storage receives Markdown. Use the `runbook-viewer` read-only variant for Issue Detail runbook display; do not fall back to ReactMarkdown or the editable runbook shell there. Server-owned issue attachments are still pending; do not reintroduce a local attachment store.
- Issue and child issue titles are plain text even when their source body or checklist row uses Markdown. The create modal derives an immediate draft title from TipTap plain text and sends it with `titleSource="plain_text"`; a missing `titleSource` is reserved for compatibility with older clients that derived a Markdown-formatted draft from the body. Creation and navigation do not wait for the final title. After project analysis is queued, the create request synchronously persists the existing priority-0 `issue_type_triage` task with the exact draft in `expectedTitle`, then returns without waiting for worker execution; Issue list/detail reads must not enqueue triage as a side effect. If an active compatibility task exists without `expectedTitle`, Memory/SQLite upgrade it under the store mutex and Postgres upgrades or creates it under an issue-scoped advisory transaction. When no active task exists, that same atomic section must recheck that the Issue is still pending and has no type label before inserting, so a stale caller cannot create a second turn after completion. Updated workers return a rewritten title alongside the type result. Stores sanitize that untrusted title through the Markdown-to-plain projection and apply it only when the current title still equals the captured draft. Human edits always win, the Markdown body is unchanged, and older title-less worker results still classify type without breaking the task. Postgres manual label updates lock the Issue row before `issue_labels`, matching worker reconciliation lock order so concurrent human type selection remains authoritative.
- Issue task lists are modeled as child issues via `issues.parent_issue_id`, then rendered inline on the parent Issue Detail page. Markdown checklist lines typed during issue creation are converted into child issues so the checkbox text is not a second source of truth.
- Server-owned issues store denormalized display fields `creator_name` and `creator_avatar_url`; comments store `author_user_id`, `author_name`, `author_avatar_url`, `updated_at`, and `edited_at`; `comment_reactions` stores lightweight human reaction rows and aggregated per-comment summaries without changing Markdown comment bodies or agent prompt history. Status-transition comments should be stored with the actor that made the change so the timeline says the human or agent performed the update, not `mspace`.
- Only the latest human-authored issue comment may be edited, and only before an agent session has consumed it. Agent-triggering sessions store `agent_sessions.trigger_comment_id` so editing cannot rewrite the prompt history of an already queued, running, completed, failed, or cancelled turn.
- Human owners and comments should render with the real stored avatar/name when available. Codex uses the shared avatar asset from `packages/views/src/agent-avatar.ts`; Claude Code and Pi use their engine identity with a quiet fallback mark until first-party assets exist. Never render a Claude Code or Pi Session as Codex.
- Imported GitHub repositories and session workdirs are worker-owned runtime details. Docker-backed workers keep those paths under the configured worker root, normally `/var/lib/mspace-worker`.
- Codex sessions start `codex app-server --listen stdio://`; Claude Code uses print-mode stream JSON with a required terminal `result`; Pi uses official RPC mode with `prompt`, `abort`, and required `agent_end`. All run inside the worker-prepared worktree, while Pi local session paths stay worker-private.
- Normal source-code agent sessions are captured as issue change nodes when they finish with git changes. If the session worktree already has an ahead-of-base commit, mspace records that HEAD commit instead of creating an extra commit. Otherwise the worker stages the worktree, excludes `.mspace` artifacts, retries transient `.git/index.lock` write conflicts during `git add`, `git reset`, and `git commit`, creates the captured source commit, and exposes commit metadata plus diff preview from Issue Detail. Before capture, agents may write `${MSPACE_SESSION_ARTIFACT_DIR}/branch-name.json`; workers normalize standard names such as `fix/pr-source-branch-selection` and rename the source branch when safe.
- Review evidence is captured separately in `session_review_evidence`. Keep code diffs and changed files in the Commits tab. The Evidence tab's default view is a read-only current review packet: verdict summary, status signals, agent summary, compact `Command evidence`, risks/follow-ups, and source/review facts. Older reviews, blockers, and Kubernetes snapshot details should be opened from full-width Evidence subpages instead of expanded in the right rail.
- Branch / PR handoff is captured in `issue_handoffs` as an issue-level delivery artifact: one issue should have one current PR, while commits are evidence/source context for that PR. The Commits tab should treat `Source branch` as the PR source identity and de-dupe multiple captured commits on the same branch. Source commit capture is always on. Workspace Settings may expose handoff automation policy plus read-only GitHub App installation status, but actual branch publishing and GitHub PR creation/refresh belong to a server-owned GitHub App executor, not a worker-local `gh` path or standalone agent GitHub account.
- Dry-run worker commits are diagnostic runtime records only. They can appear in task/session logs for smoke testing, but they should not be offered as PR source branch candidates in the Commits tab.
- Failures are captured as `session_failures`, linked to the issue, session, optional deployment evidence, and optional review evidence. Failed sessions and failed deploy/preview/cleanup reconciliation should preserve the failed command, compact error summary/excerpt, phase (`build`, `test`, `image_push`, `pod_startup`, `network_exposure`, `preview_probe`, `agent_interrupted`, or `cleanup`), and namespace/resource hints in server-owned records for internal debugging. Default Issue Detail UI should show only the user-facing error summary plus necessary Continue / Retry deploy / Stop affordances; do not expose failed commands, runtime excerpts, phase, session ids, namespace/resource metadata, or debug evidence entry points in the normal user workflow. Do not add an issue-level `failed` status for this; keep the issue in a handoff state such as `blocked`.
- Changed-file chips and rows use `packages/views/src/file-type-icon.tsx`, backed by `material-icon-theme`, so file surfaces match IDE-style file type icons.
- Agents are the three code-owned execution engines `codex`, `claude_code`, and `pi`, exposed as `@codex`, `@claude`, and `@pi`. `agent_profiles`, `@triage`, `@bugfix`, `@design`, custom Agent CRUD, and per-profile prompt instructions no longer exist. Workflow Skills remain server-managed and separate: built-ins are embedded from `mlhiter/skills`, workspace custom Skills and revisions remain persisted, and the Agents route keeps the Skills management tab. System Workflows such as triage, issue analysis, Tests, import mapping, deploy, and cleanup remain explicitly Codex-backed until a later engine policy is designed.
- Project creation is workspace-mode aware. Personal desktop workspaces may use the desktop folder picker for a local repository or a GitHub repository URL. Team workspaces must use a GitHub repository URL so connected team workers can clone source into their own repo cache and session workdirs; do not store a user's Mac-local folder path as the source for a team project. Project records live in the server store: Postgres for team/shared deployments, SQLite only for packaged personal desktop mode.
- Project runbooks are agent-discovered project memory stored in server `project_runbooks` with revision history in `project_runbook_revisions`. Projects settings are a full page, not a modal; the runbook is edited through the TipTap Markdown editor, Issue Detail shows a compact sidebar entry that opens a TipTap read-only modal, and project rows use a quiet ghost gear icon for settings. Do not reintroduce install/test/build/deploy command form fields.
- The Tests route is a workspace quality surface where Cases and Case suggestions remain project-level, while Plans and Runs are workspace-level orchestration objects that may include ready cases from multiple projects. Dedicated detail routes exist for cases, plans, and runs. Create/import case flows use modals. Imports should call the server preview endpoint first, show importable count, skipped rows, missing field counts, quality findings, source-column mappings, sample cases, and skipped-row samples, then write only after the user confirms. Markdown/text imports treat each non-empty line as one case; CSV and Excel `.xlsx` imports share the canonical `title`, `type`, `area`, `priority`, `preconditions`, `steps`, `expected_result`, `environment_requirements`, and `tags` column contract. Unknown, localized, or product-specific source columns must go through the worker-assisted import mapping task, then preview/import with explicit confirmed `columnMappings`; do not grow hardcoded language-specific aliases in the server parser. Treat business category columns such as `测试类别` as tags, not the fixed system `type`, unless a real type column is present. Historical execution-state columns may map to `latest_result` for preview context. Valid case types are `functional`, `ui`, `api`, and `deployment`; specialized UI/CDP/API/deployment harnesses are later work, but the case library can already classify those types. The server is the source of truth for browser-backed case signals and returns `requiredCapabilities` on Test Plan and Run detail responses; renderer preflight must use that map instead of maintaining a second browser-classification rule. Plans can carry lightweight free-text setup steps for real preconditions such as platform login, Kubernetes image updates, SSH/VM commands, mock data, or preview checks; do not expand this into a template library or workflow DAG yet. Case Detail revision history should compute user-readable field changes from stored revision snapshots, so users can see what changed without opening raw records.
- Test module execution stays Issue-backed. Optimizing or generating cases and starting normal test runs create Issues/agent sessions through the existing worker runtime path; normal user-visible test execution must start from workspace Test Plans, not from a single Case or selected Cases directly. Direct selected-case run APIs may remain only as compatibility/debug paths and should not be exposed as ordinary UI actions. Codex artifacts are `test-case-proposals.json`, `test-setup-result.json`, and `test-result.json`. Workspace-level runs must preserve per-item project identity and group execution sessions by project; one agent session should not span multiple repositories/projects. Plan setup runs once before case execution; only a completed passing setup starts execution sessions, while failed/cancelled/missing setup leaves run items queued and marks the run `setup_failed`. User-stopping an active test run marks the run and queued/running items `cancelled`, cancels linked runtime tasks, and must ignore late setup/result artifacts instead of reviving the run. For setup/execution tasks, a matching `test-setup-result.json` or `test-result.json` is enough for worker-side runtime completion even if Codex does not emit a final turn-completed event; conversely, a completed Codex turn without the matching Tests artifact must fail the runtime task instead of reporting success without evidence. The same worker may reclaim its own stale `running` task and recover the existing workdir instead of leaving the run stuck. Humans must accept suggestions before canonical test knowledge changes; test run accept/block decisions are lightweight review records until a later release or plan gate consumes them. These test automation Issues are audit carriers for Tests and should be hidden from the default Issues list; keep manually created `type:test` Issues visible as normal human work.
- Local sidecar APIs and renderer-owned file databases must not be reintroduced. If a feature needs persistence or collaboration truth, add it to `server/`, update the store contract, and include Postgres migrations for shared deployments. The only file-backed product store allowed right now is the server-owned SQLite personal store used by the bundled local desktop server.
- Issue statuses are explicit handoff states: `open`, `needs_review`, `changes_requested`, `ready_for_test`, `blocked`, `cancelled`, and `closed`. `cancelled` means the issue is closed as not planned; it is not used for a stopped agent session. Transient progress belongs to `agent_sessions` and `issue_test_environments`, not issue status.
- The Agents route is read-only for the fixed Agent catalog and reports runtime availability for each exact engine capability. It must not expose create, edit, enable/disable, model, MCP, arbitrary command, or prompt-profile controls. Skill management remains a separate tab.
- Issue labels use the built-in `issue_label_definitions` taxonomy and `issue_labels` links. The current dimensions are `type` and `priority`.
- New issues start with `triage_status=pending` unless a type is set manually. The server queues an `issue_type_triage` runtime task requiring `{"codex":true}`; an updated worker returns a rewritten plain-title candidate together with exactly one Conventional Commit type, while an older worker may return the type-only shape. The server conditionally applies the title and independently reconciles the type label; it does not classify by keyword or run Codex locally. Project-backed issues synchronously queue a read-only `agent_session` automation marked `issue_analysis` before asynchronous type triage starts, either at creation time or when a project is later attached; its priority 10 remains ahead of triage priority 0, so title refinement never becomes an analysis prerequisite.
- Priority labels are manual only. Do not auto-classify priority.
- Reusable environments are workspace targets with kind `kubernetes` or `virtual_machine`; preview URLs are run/deploy outputs, not environment records.
- Kubernetes environments are projected from server `clusters` compatibility records; they store kubeconfig path, optional context, registry prefix, exposure defaults, readiness status, and last check time. The Environments route imports kubeconfig files through the desktop file picker. On first empty-state entry, it discovers regular files under `~/.kube`, lists candidates and contexts, and lets the user choose which files to import.
- Virtual machine environments store SSH target metadata plus server-owned SSH credentials. Create/update accepts `sshAuth` material (`password` or `private_key`), persists it in the server store for later worker access, and never returns raw passwords or private keys in Environment responses; responses expose only `sshAuthRef` and `sshAuthConfigured`. Recheck uses the saved credential by default, or replaces it when new `sshAuth` is provided. Success marks the VM `ready`, connection/auth failure saves it as `unreachable`, and missing or unparsable auth material is rejected when no saved credential exists.
- Workers are runtime executors and are decoupled from environments. Workers claim runtime tasks by mode/capability and operate selected environments through kubeconfig, SSH references, or future provider-specific access.
- Projects keep `default_cluster_id` as the current Kubernetes compatibility default and expose `defaultEnvironmentId` as the product-facing alias; issue test deployments can override the Kubernetes environment and exposure mode per run.
- Test plans and test runs may select an environment and persist `environment_id`, `environment_kind`, and a frozen `environment_snapshot`; the existing free-text `environment` field remains notes/prompt context, not the source of truth for target selection.
- Each issue can have one `issue_test_environments` record with environment id/kind/snapshot, Kubernetes cluster id, issue namespace, namespace state, cleanup state, preview URL, deploy/cleanup session ids, selected source session/commit, registry, kubeconfig, context, exposure mode, domain, ingress class, and NodePort host. Current issue deploy/resource flows support Kubernetes environments only; VM deployment/testing is a later provider-specific execution path.
- Issue Detail has a Resources tab for live namespace inspection. It refreshes on entry and via a manual refresh button, calls `GET /api/workspaces/{workspaceID}/issues/{issueID}/test-environment/resources`, and renders only the issue's fixed test namespace: Pods, Services, Deployments, Ingresses, and recent Events. Do not add frontend namespace input, cross-namespace browsing, Secrets, Nodes, or other cluster-wide inventory to this tab.
- Deploy/test reconciliation captures Kubernetes evidence, discovers preview candidates, checks the selected preview URL, updates the issue test environment to `active`, `preview_unverified`, `deploy_failed`, `deploy_interrupted`, `cleanup_failed`, or `cleaned` as appropriate, and records a `session_failures` row when the environment needs attention. When workspace `autoDeployTestEnvironment` is enabled, a successful non-dry-run source session with a captured commit can queue exactly one follow-up deploy/test session for that source commit, provided the issue has a project, deploy settings can be resolved, and a matching active Codex worker is online.
- Preview verification should stay internal and background-driven. Issue Detail automatically refreshes preview status when an environment is present; do not expose a user-facing `Probe` button.
- Deploy/test sessions receive resolved Kubernetes and preview values through `KUBECONFIG`, `MSPACE_KUBECONFIG`, `MSPACE_CLUSTER_ID`, `MSPACE_KUBE_CONTEXT`, `MSPACE_KUBE_NAMESPACE`, `MSPACE_TEST_NAMESPACE`, `MSPACE_IMAGE_REGISTRY_PREFIX`, `MSPACE_EXPOSURE_MODE`, `MSPACE_PREVIEW_DOMAIN`, `MSPACE_INGRESS_CLASS`, and `MSPACE_NODE_HOST`. Environment identity/kind/snapshot remain server records and prompt context; preview URLs remain outputs.
- Sessions also receive `MSPACE_API_BASE_URL`, `MSPACE_ISSUE_ID`, `MSPACE_SESSION_ID`, `MSPACE_AGENT_TOKEN`, `MSPACE_AGENT_ENGINE`, `MSPACE_SESSION_BRANCH`, `MSPACE_SESSION_WORKDIR`, `MSPACE_SOURCE_SESSION_ID`, `MSPACE_SOURCE_COMMIT_SHA`, `MSPACE_SESSION_CONTEXT`, `MSPACE_SESSION_ARTIFACT_DIR`, `MSPACE_REPOSITORY_URL`, `MSPACE_PROJECT_REPOSITORY_PATH`, and `MSPACE_PROJECT_SUBDIR` when available.
- Tailwind CSS 4 scans monorepo UI packages through `@source` entries in `apps/desktop/src/renderer/src/globals.css`.
- shadcn/ui semantic tokens are mapped to the Notion-like mspace palette through `@theme inline` in `apps/desktop/src/renderer/src/globals.css`.

## Working Rules

- Keep Inbox and Issue objects as first-class product objects.
- Keep Inbox read state per-user and event-based. Do not add new product behavior that depends on a global issue-level unread boolean.
- Keep task lists as inline child issue views, not Markdown checkbox state.
- Humans do not choose general top-level workflow states from the Issue sidebar. The sidebar status is read-only; human lifecycle actions live inside the Issue Detail comment composer footer.
- Stopping a queued or running session cancels only that `agent_sessions` row and records a compact, non-editable session event. It must not change the Issue status or treat the whole Issue as discarded.
- Keep Inbox review-only. New issue creation belongs in the Issues flow, not in Inbox.
- Keep issue creation minimal: note only. Project routing is optional at creation time.
- Require an attached project before agent execution, PR handoff, test environments, or project runbook access.
- Keep type triage asynchronous. Issue creation must not wait for agent classification.
- Do not use keyword matching for issue type classification; use the triage agent and validate its structured output against the fixed type set.
- Keep project runbooks as the only user-facing place for project operation knowledge.
- Keep multiplayer identity and collaboration authority in `server/`, not in the desktop renderer or any local sidecar.
- GitHub OAuth should prove identity only. Local password login is a product identity fallback for restricted environments. The product session should always be an mspace-issued token, and future GitHub repository automation should use GitHub App installation tokens owned by `server/`.
- Keep `server/` independent from Agent runtime dependencies. The deterministic `suggest-title` endpoint remains a compatibility/fallback API; normal final-title refinement is returned by the Codex-backed `issue_type_triage` task. Any LLM-backed classification or Agent turn must go through runtime tasks, and user Agent turns must require the selected engine's exact active Worker capability.
- For Codex-backed worker sessions, prefer `codex app-server --listen stdio://` over `codex exec`.
- Codex-backed worker sessions should not start or keep development servers running by default, and should not report container-local `localhost` or `127.0.0.1` URLs as user-facing previews.
- Keep Kubernetes as the default deployment and test environment.
- Do not rely on Sealos UI APIs as the primary control path.
- Prefer namespace-scoped operations and explicit RBAC.
- Treat `kubectl` as acceptable for agent-run deploy prototypes, but prefer structured Kubernetes APIs for durable product logic.
- Do not design cluster-wide agent permissions.
- Do not let agents read Secrets by default.
- Every write-capable session must have an audit trail and a cleanup path.
- Do not fork Multica; use it as a structural reference only.
- Keep docs current when product decisions change.
- Keep `apps/website/src/changelog.ts` current when a task ships meaningful product, engineering, documentation, or website progress.
- Product UI must stay user-centered: show the user-facing meaning, decision, and next useful action; hide raw implementation details, tokens, ids, protocol states, and debug-only metadata unless the user is explicitly debugging or operating an admin surface.
- Do not ask users to operate things they do not care about. If the system can carry state from a link, session, server capability, or workspace context, do that automatically instead of exposing an input, code, or configuration knob.
- Preserve the quiet Notion-like workspace style: document-first, low-contrast paper surfaces, compact rows, restrained icon buttons, and no decorative dashboard or marketing layout.
- Do not use persistent left-list/right-detail split panes for object browsing. Lists should open object details on dedicated pages with their own route and breadcrumbs; keep sidebars only for narrow metadata on explicitly designed overview pages.
- Visible product copy in desktop, UI, and view packages should be locale-aware through `@mspace/i18n` when it belongs to the shell or main workflows.
- Treat `DESIGN.md` as the first reference for UI style, tokens, component rules, and visual guardrails.
- Never execute database write operations unless the user explicitly asks for database modification.
- Do not delete session workdirs or git worktrees unless the user explicitly asks for cleanup through the product or the current conversation.

## Preferred Vocabulary

- Workspace: the team boundary for members, issues, agents, and runtime policy.
- Inbox Event: server-side review fact for issue activity; per-user receipts determine unread state.
- Inbox Item: per-user review item derived from workspace issue-event receipts.
- Project: a repository plus runtime policy.
- Environment: a reusable workspace target with kind `kubernetes` or `virtual_machine`, operated by decoupled workers.
- Issue: the durable collaboration document for one unit of work.
- Agent Session: one agent run attached to one issue.
- Issue Test Environment: the per-issue validation record; currently Kubernetes namespace lifecycle plus environment snapshot and preview output.
- Project Namespace: a long-lived namespace owned by one project.
- Issue Namespace: a namespace created and managed for one issue's test deployment.
- Runtime Provider: the mechanism that starts the agent workspace.
- Server Worker Runtime: a fixed team-owned server, VM, DevBox, or shared machine running the worker daemon for non-Kubernetes teams.
- Kubernetes Runtime Provider: the advanced team runtime form that starts isolated per-session Pods or Jobs while preserving the same runtime task protocol.
- Scoped Kubeconfig: kubeconfig bound to a session ServiceAccount and namespace policy.

## Product Taste

The UI should feel operational, document-first, and close to Notion's quiet workspace language. Avoid marketing-heavy pages, decorative dashboards, and abstract AI terminology. The first screen should help a developer answer:

- Which issues need attention now?
- Which agent sessions are attached to each issue?
- What is the agent doing now?
- Which runtime and namespace is it operating?
- Where is the environment?
- What branch or PR did it produce?
